# 消息文本方向（RTL）

## 目标

阿拉伯语、波斯语、希伯来语等从右到左（RTL）文本在对话中按内容自身方向显示。混合方向的消息逐块判断方向，不跟随应用界面语言，也不把整条消息强制为单一方向。

## 范围

- 所有复用 `MessageResponse` 的 Markdown 表面（Assistant 正文、分享页、工具卡片正文、计划与发布说明等）。
- 用户消息气泡正文：`ConversationUserInputBody` 的可折叠正文容器。
- 不包含：应用整体 RTL 镜像、i18n、输入框编辑器、工具卡片外壳、时间线左右对齐和气泡尾角位置。

## 方向规则

`MessageResponse` 的 `dir` prop 取值 `"auto" | "ltr" | "rtl"`，缺省为 `"auto"`。

| 元素             | `dir` 属性                                            |
| ---------------- | ----------------------------------------------------- |
| `p`、`h1`–`h6`   | `dir` prop 的值                                       |
| `ul`、`ol`       | `dir` prop 的值；`li` 不单独设置，继承列表方向        |
| `th`、`td`       | `dir` prop 的值                                       |
| 代码块、行内代码 | 固定 `ltr`，并借助 `dir` 属性的 bidi 隔离保持符号顺序 |
| `blockquote`     | 不设置，由内部段落各自判断                            |
| 用户气泡正文容器 | `auto`                                                |

- `auto` 交给浏览器原生 first-strong 算法逐元素判断，流式态与完成态结果一致。
- 显式传入 `ltr` / `rtl` 时，上述文本块统一使用该值；代码仍固定 `ltr`。
- 不使用 Streamdown 自带的 `dir`：static 模式下它只在根节点按整条消息的首个强方向字符计算一次，streaming 模式下才逐块计算，完成时会出现方向跳变，也无法处理同一条消息内的多方向段落。
- `li` 不设置 `dir`：浏览器计算 `dir="auto"` 时会跳过自身带 `dir` 的后代，若 `li` 也带 `dir`，`ul`/`ol` 将检测不到任何文字而回落为 `ltr`，marker 与缩进会落在错误一侧。

## 布局

只有接收方向内容的元素改用逻辑属性，使 LTR 渲染保持不变：

- 无序列表缩进 `pl-5` → `ps-5`，RTL 列表的 marker 位于右侧且不被气泡 `overflow-hidden` 裁剪。
- 列表项 `pl-1` → `ps-1`，marker 与正文的间距跟随方向。
- 表头 `text-left` → `text-start`。

不接收方向内容的元素保持物理属性：用户气泡外壳的 `rounded-tr-xs` 尾角、消息行右对齐、引用块左边框、代码块头部内边距。

## 已知边界

- 松散列表（列表项内容包在 `<p>` 中）：段落各自带 `dir`，列表本身检测不到文字而回落为 `ltr`，文字方向正确但 marker 在左侧。与 GitHub Markdown 渲染行为一致。
- 引用块竖线固定在左侧。
- 用户气泡正文按整段首个强方向字符判断一次；多行混合方向时以首个强字符为准。
- 表格列顺序不镜像，仅单元格内文字按自身方向对齐。

## 验收

- 纯阿拉伯语回复：段落、标题、列表右对齐，无序列表 marker 在右侧且完整可见。
- 阿英混合回复：每个段落、标题、列表和单元格按自身首个强方向字符对齐。
- 阿拉伯语段落中的行内代码 `foo()` 与代码块保持 LTR 显示。
- 用户发送阿拉伯语或希伯来语消息：气泡内文字右对齐，气泡仍位于时间线右侧。
- 仅含 LTR 内容的消息渲染与修改前一致。
- 单测：`packages/ui/test/messageTextDirection.test.ts`。
